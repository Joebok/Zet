# Migrate Character Pipelines to shared image production
Status: complete
Related issue/specification: [Image Production Abstraction](../../Docs-Joe/Image%20Production%20Abstraction.md)

## Goal
Move Body Reference, Head Image Construct, Head Image Edit, Character Assembly, and Costume Dressing from batches to persistent Asset Containers with one eight-slot Candidate Board per view. Keep character prompt compilation, template improvement, source choices, character identity and Inventory metadata. Use the [Narrative Subscene workflow](../../Docs/DECISIONS/0047-narrative-candidate-board-handoff.md) as the implementation reference for everything from candidate allocation through human review, selection and locking. Retire batches, batch actions, the Batches page and the Character Activity list. Defer Luna rankings to separate follow-up work after the basic workflow is established.

## Current behavior
The Character dashboard now uses persistent Asset Containers with one mixed-quality Candidate Board per view. Requests are prepared from current masters and ordered references, dispatched and harvested through the shared `ImageProductionService`, and reviewed and published from the board. The Assets UI has manual render controls, comparisons, candidate-backed template proposals, and compact active-view polling. Legacy batch routes and startup recovery are retired; historical files remain for migration and rollback compatibility.

The shared image-production workflow is implemented across Character and Narrative. Character-specific authoring, board persistence, and Inventory publication remain behind their adapters. Moonsea's reviewed live migration is complete: 48 locked views and 9 phase-source choices were imported into 10 containers. Disposable fixtures and the approved four-scenario E2E suite cover the implementation and browser workflow.

## Desired behavior
Each container is scoped by universe, character, phase, pipeline, and costume when Dressing. Each view owns one mixed-quality board. Shared character assets and view-specific reference choices belong to the container. New requests freeze prompt, ordered input images, settings, seed, and provenance. Locks publish immediately to Inventory. Existing valid Final locks seed migrated boards. No batch/activity workflow remains for Character Pipelines.

## Shared render boundary clarified 2026-11-06
Each pipeline owns authoring: it compiles the prompt and marshals ordered reference images into a quality-specific `ImageRenderRequest`. On an explicit operator action, the common image-production service queues the request on demand. The common service owns queue submission, progress/recovery, harvest into the candidate image slot, and shared review controls such as selection, clear/delete, regenerate/retry and previous/next navigation. Quality is a request setting. There is no batch runner, scheduled multi-view generation, or automatic render entry point.

Character keeps its side-by-side comparison as pipeline-specific review context around the shared board controls. The operator can choose one or more available comparison images. Choices may include the selected FRONT view and, when available, the selected opposite-side view. Selected or locked Draft images are excluded from comparison choices. Candidate slot, selection, lock and common review behavior remain consistent across Character, Narrative Scenes and Minor Characters.

## Reuse boundary and cutover gates

- **Character authoring** owns the brief, current masters, template proposals/diffs/acceptance and conflict-checked master promotion, view recipes, source choices, and prompt compilation. Keep the useful authoring behavior, including explicit template improvement from image evidence where supported. Bind it to the container/view, not a batch or mandatory approval stage. A template trial that renders uses shared image production; accepting an edit affects new requests only.
- **Shared image production** owns the image lot: slot allocation and stable positions, staging/dispatch, progress, harvest/recovery, retry and replacement, the cards and human review of the candidate and its submitted prompt/references, selection, locking, and protected clear. The handoff is a frozen `ImageRenderRequest` for a scoped target/candidate. A render submission may group jobs internally, with no separate operator lifecycle. Character supplies its Inventory destination and metadata through a publication adapter; the board is authoritative for the current selection and lock.
- **Keep legacy workflow out of the new path.** Do not call legacy run creation, per-mode boards, batch/stage progression, front-first approval gates, Run All Remaining, automatic evaluation/refinement, batch recovery or batch status from the container workflow. Resolve genuine input prerequisites only when preparing a new request. Legacy readers may support import and narrow Inventory compatibility; legacy IDs, locks and workflow state must not drive board actions. Inspect the runtime call paths as well as the visible UI before cutover.
- **No Luna rankings in this migration.** No ranking dispatch, ranking data import or display, re-evaluate actions, or ranking-triggered refresh. Humans can review, select and lock as soon as an image is available. Template improvement remains an explicit authoring action. A later change may add optional advice without changing physical slots or gating human decisions.
- **No additional page polling.** Use one existing image-slot progress mechanism, adapted/shared from the Narrative target path if needed. It is the only recurring fetch on the new Character pages: compact progress for the visible board while its slots have active render work, with detail refreshed when work settles. Do not carry forward the legacy batch summary timer's evaluation/operation triggers or add a poller for authoring, readiness, sources, reviews, Inventory, other boards, or workspace summaries. Refresh those on entry, relevant actions, tab return or explicit request. Opening a review must not start another loop. Server-side queue and harvest protections remain in force.

## Invariants and constraints
Preserve universe isolation, stable slot membership, ownership and attempt fencing, ordered reference bindings, captured retry inputs, immutable Inventory outputs, and publication recovery. Apply image source freshness only when preparing new work, following ADR 0045. Keep Minor Characters and standalone Image Generation unchanged. Use isolated fixtures and prepared answers. Do not add maintained tests or run live rendering.
