# Character pipeline validation, guards, and polling inventory

Review draft — 2026-11-02. This is an analysis of the current working-tree code, not an approved behavior change. It covers the five batch-based local pipelines: Body-Reference, Head-Image (Construct), Head-Image (Edit), Character-Assembly, and Costume-Dressing. Minor Characters, Image Generation, and Narrative Scenes have independent workflows. Character Overview, Batches, Activity, and the two auxiliary character review pages are included because they poll or load these batches.

## Reading the recommendations

| Recommendation | Meaning |
| --- | --- |
| Keep at action | Validate when creating, preparing, selecting, locking, publishing, or saving. The check protects the action's actual inputs or saved work. |
| Move to pre-render | Show the result once, immediately before submitting new renders; recheck under the preparation lock if inputs changed. Do not keep reporting it after an image exists. |
| Manual comparison | Provide an explicit **Check vs Draft** or **Check vs masters** report. A difference is information, not automatic failure. |
| Reduce read/poll | Keep the state visible, but compute or fetch only what the open page needs. |
| Review guard | The present rule may obstruct selecting/locking a useful finished image after a reference changes. Decide its product policy before changing it. |

The working preference is to move forward with better images. Final may start from Draft templates and prompts and then diverge. New renders must use the explicitly chosen current masters or batch version and current eligible reference images. Completed renders retain their frozen prompt and input record; changing masters or references later should not silently rewrite them. A pre-render confirmation should name the chosen template version, the views whose prompts were updated, and each resolved reference identity/mode. It must list blocked views separately; it cannot say “all references are current” for a view whose required reference is missing. Existing queued asks remain frozen. These are recommendations, not statements that the current UI already provides one consolidated confirmation.

The clearest recurring-cost candidates found in source are the all-view/two-mode detail projection, per-candidate file/queue inspection, Assembly/Dressing recursive lineage reads, and Costume-Dressing's full-byte SHA-256 of its Assembly snapshot inside a readiness function called for multiple views/modes/settings. Their actual contribution to latency was not measured. [Detail projection](../zet/services/local_image_workflow_service.py#L489), [lineage](../zet/services/local_character_asset_pipeline_service.py#L601), [Costume readiness](../zet/services/costume_render_mode_service.py#L27).

## Preliminary decisions for review

1. **Retain action-time safety:** universe/character/costume ownership, valid view/mode, current slot membership, selected/locked protection, missing image checks, operation/attempt fencing, frozen ordered inputs, and atomic master/publication writes.
2. **Consolidate pre-render feedback:** after **Use current masters**, compile every eligible view prompt from that choice, resolve each view's current reference identities, and report updated/blocked views once. New render preparation rechecks under its existing lock and freezes the exact prompt and reference bytes. If any view is blocked, report partial readiness explicitly rather than claiming all prompts/references are current.
3. **Offer manual comparisons:** **Check vs Draft** for Final prompt/template differences; **Check vs masters** for current batch prompt/template differences; **Check references vs current** for captured render sources versus today's selections/locks. These reports do not invalidate completed candidates.
4. **Revisit historical-source lock guards:** Head-Edit guide freshness and Assembly/Dressing lineage checks are potentially at odds with selecting/locking a better finished image after upstream work changes. Keep the finished image and its frozen provenance available while deciding which publication checks are essential to catalog integrity.
5. **Separate automatic work by page:** batch summary polls compact progress/selection; view page polls the current view; open review jobs get conditional polling. Global Batches, Overview and Activity use active-work cadence rather than fixed rapid polling when idle.

## Limits and next review

This is a source inventory, not a runtime profile or exhaustive path-by-path proof. No completed Final batch or live renderer was used. Some legacy adapter branches differ from new mode-scoped selection/lock routes; the review recommendations call those out rather than assuming one uniform rule. Before changing guards, trace their downstream publication consumers and decide whether frozen render provenance can be sufficient. The approved choices and validation are recorded in [the completed batch/view split plan](../plans/completed/character-pipeline-batch-and-view-pages.md). No behavior changes were made for this inventory.
