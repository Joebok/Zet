# Zet Pipeline

Zet is a web-based dashboard tool for managing image assets and the processes used to create those images.

Zet is organized around a set of characters. Each character has at least one phase. A phase is usually a life stage, such as `Adult` or `Youth`, but it may represent any useful subdivision of a character.

In practical terms, `Character` and `Phase` identify the filesystem location where that character-phase’s specifications, asset records, and pipeline records are stored.

## File Organization

`config.toml` sets the base paths:

```toml
[BaseFolders]
BaseCharacterPath = "_Lib/Characters/"
BaseAssetPath = "_Lib/Assets/"
BasePipelinePath = "_Lib/Pipelines/"
BaseAIQueuePath = "_Lib/AI_Queue/"
```

Derived paths are determined from asset fields:

* `CharacterPath` = `BaseCharacterPath / Character / Phase`
* `CharacterAssetPath` = `BaseAssetPath / Character / Phase`
* `PipelinePath` = `BasePipelinePath / Character / Phase / Pipeline / BodyView / HeadView`

`HeadView` is optional. If `HeadView` is blank, it should be omitted from `PipelinePath`.

All derived paths are programmatically determined from the fields above.

## Characters

A character in a phase has a set of specifications, assets, and pipelines.

Specifications are Markdown files stored in `CharacterPath`.

`Assets.json` is stored in `CharacterPath`. It contains the asset records for the selected character-phase.

`Pipelines.json` is stored in `CharacterPath`. It contains pipeline configuration, state-transition rules, actor assignments, and other pipeline-specific properties for the selected character-phase.

An asset represents an image file in `CharacterAssetPath`. Asset images are generated by executing a pipeline and then, after human review, promoting the candidate image to `LOCKED`.

Intermediate files used during asset production are stored in the asset’s `PipelinePath`.

Python scripts inspect, read, and write files in these folders.

## Asset Overview

An `Asset` is a record that represents one intended final image.

Each asset belongs to:

* one `Character`
* one `Phase`
* one `Pipeline`
* one `BodyView`
* optionally one `HeadView`
* optionally one `Costume`
* optionally one `Expression`

A completed set of assets for a given `Pipeline` may form a turnaround set. A turnaround set is a series of images showing the character from the required viewpoints for that pipeline.

Each asset has state fields that track its progress through the generation and review workflow.

### `AssetState`

`AssetState` indicates the overall status of the asset.

Allowed `AssetState` values are:

* `NEW` — the asset has not been started.
* `IN_PROGRESS` — the asset is currently moving through a pipeline.
* `LOCK_REVIEW` — the candidate image has completed pipeline processing and is waiting for human review.
* `LOCKED` — the candidate image has been approved and promoted to `CharacterAssetPath`.
* `ERROR` — the asset requires human investigation due to an ERROR in the pipeline.
* `BLOCKED` — the asset requires human investigation before processing can continue because something went wrong.

### `PipelineStage`

`PipelineStage` indicates the detailed stage of the image-generation process.

Allowed `PipelineStage` values are:

* `MANIFEST`
* `PROMPT`
* `PROMPT_REVIEW`
* `GPT_HANDOFF`
* `RENDER`
* `RENDER_REVIEW`
* `ERROR`

The usual pipeline flow is:

```text
MANIFEST -> PROMPT -> PROMPT_REVIEW -> RENDER -> RENDER_REVIEW
```

`PROMPT_REVIEW` is optional.

`GPT_HANDOFF` is used only for pipeline stages that require a human-facing or AI-facing handoff outside the normal local-rendering flow.

When pipeline processing is complete, `AssetState` is set to `LOCK_REVIEW`. The asset then waits for a human agent to either promote the candidate image to `LOCKED` or send the asset back for regeneration.

## Python Scripts

Python scripts govern progression through `PipelineStage`.

In general, `AssetState` is controlled by humans operating the dashboard. Human actions may invoke state-change scripts that update `AssetState`, `PipelineStage`, or both.

Most scripts govern pipelines and fall into one of the categories below. Each script receives the asset it is operating on, plus any additional parameters needed for the specific action. Error indicators may also be passed to state-change scripts.

### Polling Scripts

A polling script scans the asset table for records matching specific conditions and takes the appropriate action.

Polling scripts may be invoked manually from the dashboard.

Each pipeline may have its own polling script.

Polling scripts call worker scripts.

### Worker Scripts

A worker script performs the work required for a specific asset and `PipelineStage`.

When the work is complete, the worker script calls the appropriate state-change script.

Worker scripts may pass error indicators to state-change scripts.

Each pipeline and `PipelineStage` will usually have a dedicated worker script.

### State-Change Scripts

A state-change script validates the work done by a worker script and updates the asset record.

A state-change script may:

* advance `PipelineStage`
* set `Actor`
* set `PipelineStage` to `ERROR`
* update `AssetState`
* pass error information forward
* call housekeeping after the state change is complete

State-change scripts are called by worker scripts and by dashboard actions.

### Housekeeping Scripts

A housekeeping script prepares `PipelinePath` for the assigned `PipelineStage`.

Housekeeping runs after a state-change script has updated `PipelineStage`.

Housekeeping may create folders, copy resources, clear stale intermediate files, or prepare stage-specific input files.

### AI-Handler Scripts

For pipeline stages where `Actor = AI_AGENT`, an AI-handler script manages the asset’s `AI_State`.

The AI-handler is responsible for:

* preparing `PipelinePath`
* generating AI request files
* queueing the asset for the AI manager
* processing `AI_State` changes invoked by the AI manager
* calling the appropriate state-change script when AI work is complete

### Batch Scripts

A batch script performs an action across multiple assets.

Batch scripts may iterate through asset records and call state-change scripts, worker scripts, or other pipeline scripts as needed.

Batch scripts are used for operations such as regenerating all assets for a pipeline.

## Pipeline Details

An asset belongs to a designated `Pipeline` for a designated `Character` and `Phase`.

Each asset also specifies view information used by worker scripts:

* `BodyView`
* `HeadView`

The asset record determines the file and path information needed to complete pipeline work, including the asset’s `PipelinePath`.

Current `Pipeline` values are:

* `Body-Reference`
* `Head-Fitment`
* `Character-Assembly`

Future `Pipeline` values may include:

* `Costume-Fitment`
* `Expression`

Each asset has a `PipelineStage` governed by state-change scripts.

Each `PipelineStage` has an assigned `Actor`.

The `Actor` for each `PipelineStage` is configurable through a lookup table in `CharacterPath`, usually stored in `Pipelines.json`.

When a state-change script runs, it sets the next `PipelineStage` and assigns the appropriate `Actor`.

## Actors

Allowed `Actor` values are:

* `PYTHON`
* `AI_AGENT`
* `HUMAN_AGENT`

### `PYTHON`

If `Actor = PYTHON`, the asset is eligible for processing by a polling script.

The polling script identifies the asset and calls the appropriate worker script.

### `HUMAN_AGENT`

If `Actor = HUMAN_AGENT`, a human must perform an action on the dashboard.

Human actions may include:

* reviewing a prompt
* reviewing an image
* investigating an error
* promoting a candidate image to `LOCKED`
* requesting regeneration

For a review action, the human indicates either `Pass` or `Fail`.

If the human selects `Pass`, a Python state-change script advances the pipeline.

If the human selects `Fail`, the human selects the `PipelineStage` to revert to. A state-change script then updates the asset record, calls housekeeping, and prepares the asset for further processing.

### `AI_AGENT`

If `Actor = AI_AGENT`, a Python AI-handler script prepares the request and queues it for AI processing.

AI jobs run asynchronously, so the asset uses `AI_State` to track request status.

Allowed `AI_State` values are:

* `ASKED`
* `WAITING`
* `ANSWERED`

The AI-handler sets `AI_State` to `ASKED`.

The AI manager prepares prompts and resources, sends the request to an AI model, and sets `AI_State` to `WAITING`.

The AI manager polls for returned answers. When an answer is found, the AI manager stores the result, sets `AI_State` to `ANSWERED`, and invokes the appropriate state-change script.

## Asset Fields

### Key Fields

Every asset tracks an intended final image identified by these fields:

* `Character`
* `Phase`
* `Pipeline`
* `BodyView`
* `HeadView`
* `Costume`
* `Expression`

Together, these fields form the logical asset key.

If easier for processing, an `AssetID` field may be added as a stable internal identifier.

### State Fields

Every asset has state fields governed by state-change scripts:

* `AssetState`
* `PipelineStage`
* `Actor`
* `AI_State`

Allowed values for these fields are defined above.

### Processing Fields

Additional fields used for pipeline processing include:

* `Final_Image_Output` — the filename the completed asset will have in the filesystem.
* `Last_AI_Update` — a string containing date, time, and a status message. Example: `2026-06-27 14:10 - Waiting for 45 minutes...`

The AI manager is responsible for updating `Last_AI_Update`.

## Dashboard

The dashboard is a Streamlit site that shows asset records and supports human pipeline actions.

The dashboard works with one `Character` and `Phase` at a time.

The list of available characters and phases should be drawn from the filesystem by inspecting possible `CharacterPath` locations.

The dashboard should show `Character` and `Phase` dropdowns at the top of the screen.

## Main Tab

The main tab shows the asset list for the selected `Character` and `Phase`.

The table shows:

* all key fields except `Character` and `Phase`
* all state fields
* important processing fields

Selecting a row shows the image or images associated with that asset.

If an image named `Final_Image_Output` exists in `PipelinePath`, show it under the table on the left with the caption `Candidate`.

If an image named `Final_Image_Output` exists in `CharacterAssetPath`, show it on the right with the caption `Locked`.

If a candidate image exists, show these buttons:

* `Promote to LOCKED`
* `Regenerate`

Both buttons invoke asset state-change scripts.

`Promote to LOCKED` copies or moves the candidate image from `PipelinePath` to `CharacterAssetPath` and sets `AssetState` to `LOCKED`.

`Regenerate` sends the asset back to the appropriate earlier `PipelineStage`.

## Pipeline Tab

The pipeline tab shows pipeline-specific asset status.

At the top of the tab, show a dropdown of all available `Pipeline` values.

The selected `Pipeline` determines which asset rows are shown.

On the same line as the dropdown, show a `Regenerate` button. This invokes a batch script that sends all visible assets for the selected pipeline back to `MANIFEST`.

Next to that, show a `Poll Pipeline` button. This invokes the polling script for the selected pipeline.

The table shows:

* `Pipeline`
* `BodyView`
* `HeadView`
* `PipelineStage`
* `Actor`
* `AI_State`
* `AssetState`

Rows that require human action should be highlighted when `Actor = HUMAN_AGENT`.

When a row is clicked, show the full asset record except for:

* `Character`
* `Phase`
* `Pipeline`

If `PipelinePath` contains prompt files matching `Prompt_*.md`, show them above the asset detail view as clickable links. Clicking a prompt file displays its contents.

## AI Manager Tab

The AI manager tab shows assets where `Actor = AI_AGENT`.

The table shows:

* `Pipeline`
* `BodyView`
* `HeadView`
* `PipelineStage`
* `AI_State`
* `Last_AI_Update`

When a row is clicked, show the full asset detail view, using the same detail display as the pipeline tab.

Above the detail view, show a `Retry` button.

The `Retry` button calls the AI-state manager and sets `AI_State` back to `ASKED`.

## AI Manager

The AI manager is a filesystem proxy for making AI requests to local LLM models.

The AI manager watches the AI queue folder and processes queued AI requests.

### AI Queue Path

The AI queue path is determined by:

```text
BaseAIQueuePath
```

Each queued AI request should receive its own request folder.

The request folder should contain a copy of the relevant `PipelinePath` files needed by the AI model.

### AI State Changes

Allowed `AI_State` values are:

* `ASKED`
* `WAITING`
* `ANSWERED`

`ASKED` means the asset has been queued for AI processing.

When `AI_State = ASKED`, a copy of the asset’s `PipelinePath` is placed in the queue folder.

`WAITING` means the AI manager has sent the request to an AI model and is waiting for a response.

`ANSWERED` means the AI manager has received a response and stored the result in the appropriate location.

After setting `AI_State` to `ANSWERED`, the AI manager invokes the appropriate state-change script so the asset can continue through the pipeline.

### AI Manager Responsibilities

The AI manager is responsible for:

* finding queued requests
* preparing AI model input
* sending requests to the configured AI model
* tracking request status
* writing returned output files
* updating `AI_State`
* updating `Last_AI_Update`
* invoking state-change scripts when AI output is available

The AI manager should not directly advance `PipelineStage` except through the appropriate state-change script.
