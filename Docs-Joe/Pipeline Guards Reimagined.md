Gates, Validation, Polling Guidance

There are too many obstacles, unactionable error messages, and polling/checking going on.

Important questions
- If I push this button, will a locked image be deleted?
- If I push this button, will a selected image be deleted?
- If I push this button, will a locked image be unlocked?
- If I push this button, will a selected image be unselected?

When I queue images, they should ALWAYS use
- the most recent reference image
- the most recent template

There can be helpful hints or markers on images when they were generated by what is now an outdated template or image.
This should be kept track of in the most economical way possible so that it is fast to check. If it is too slow, then checking should only be done when it is needed to be know by an action, or if I manually request it.

The template improvement process should always target updating and saving the master governing template(s). It has not been helpful to try to maintain view specific ones. Template improvement should not be mandatory, I should be able to start generating images immediately with whatever the current master are. Going through the template improvement process should work as it does now - except always when accepted, updates the master. 

The view always update their prompts from the master, and always use the most recent reference images. I should not have to take an extra step to do a re-compile. So that checkbox can be eliminated. If there is an efficient way to track the versioning so that if the current prompt and reference images are already known to be be current, then that can be done instead of a recompile - but if compiling is faster than checking, then just compile.

There may be times when I have some images made with one template, then I add new slots that use a different template. That is fine. As above, if it is quick and easy, the outdated ones can be tagged. If after review, I decide to select/lock one of the ones made with an outdated template or images, that is fine. 

If it turns out these tags are quick and easy, they must also be compute-once operations - that is, once an image has been tagged out made from outdated source materials, it will retain that tag forever - does not ever need to be checked again.

And the tags must not be scary - they are "FYI". Small and subtle.

Once a view has a locked image, then none of the other candidates need to be checked. They can be ignored by any polling or validation.

## Applicability

This was written with character pipelines in mind. However, the general principles should be present in all the pipelines including Minor Characters and Narrative Scenes. 

Both of these pipelines, however, were developed later and facilitate a rapid iteration approach with few, if any, of the main character pipelines. Narrative Scenes tag images when they were generated from different prompts than is currently entered, and Minor characters has a narrow focus of getting to an acceptable image and then not worrying about the rest. 

The character pipelines are more robust because they need to be more versatile, but this robustness can be captured in the images and the templates that hold the descriptions that were used to generate those images. 

I want all the pipelines to share the same philosophy.

## Draft and Final

Draft and final modes are new, I have not fully explored them - mostly just with Character Pipelines so far. The main thing here is that because of the long render times, we iterate on drafts to capture the words in the templates which will be used to generate final images. The end product of draft mode is more the templates than the images - the images are the proof of the templates. But that does not mean the templates need to be guarded from change or that there needs to be strong relational ties between the draft images and the templates. If I want to take a character back to draft stage, I will be regenerating with the current templates to do quick iterations to bring refinements back to final. Old versions of the draft images and templates are not important. I will have snapshots backed up outside of Zet if I really do need to go back, but it isn't the job of Zet to preserve the origins and history of images or templates.
